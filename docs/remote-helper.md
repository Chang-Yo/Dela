# 远端工具服务（helper）规划草案

日期：2026-10-09。状态：**草案，未实施**。前置：`docs/remote-projects.md`（阶段 0–4 已实施并实机验证）。本文只写规划，不含实现，不动核心代码。第二轮修订：吸收一份外部审阅意见（见文末「审阅意见处理」）。

## 结论（已定）

- helper 用 **Go** 写，纯静态二进制（`CGO_ENABLED=0`），一个架构一个文件。
- 只有**两种执行方式**：helper 通道（主）与现有的一次性 ssh（引导 + 降级）。**不做**常驻 shell 协议档。
- **不在远端跑 Agent**：内核、模型密钥、会话 JSONL、系统提示仍在本机。
- 远端项目内**不支持新建笔记**（用户已接受）；**文件预览要做**。
- 实施顺序：**6.0 远端文件身份已实施**（2026-10-09）；接着做最小 helper，然后上下文与 skills，最后 watch 与预览。

## 为什么需要 helper（实测依据）

| 事实                       | 证据                                                                                                                                                           |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Windows 客户端没有连接复用 | `ssh -o ControlMaster=auto -o ControlPath=…` → `getsockname failed: Not a socket`；`ssh -O check` 同样失败                                                     |
| 每次调用都要新握手         | 实测同一主机：常规 0.3–0.6 秒/次，冷启动 4.2 秒/次。30 条并发握手 6 秒内全部成功                                                                               |
| 能力缺口（跟握手无关）     | 无文件监听、无法只取文件片段、二进制要 base64、`ls` 逐条 stat 只能靠 10 秒缓存、长任务无法取消                                                                 |
| shell 行为差异             | 列目录依赖 GNU `find -printf`（无 GNU find 时退 `ls -A1p`）；远端普遍没有 `rg`；命令输出的编码/截断全在本机处理                                                |
| 远端环境（采样一台）       | Ubuntu 24.04.5 / x86_64 / glibc 2.39 / root；`node v24.21.0`、`npm`、`python3`、`gcc`、`curl`、`tar`、`sha256sum`、`setsid`、`nohup` 均在；无 `rg`、无 `socat` |
| 回环 + 隧道可行            | 远端 `127.0.0.1:19999` 监听成功；**本地 `ssh -L` 转发未完成实测**，实施第一步补测                                                                              |

**结论**：helper 的理由是**握手延迟 + 能力缺口 + 命令语义差异**，不是「主机拒绝并发」。既然 Windows 侧拿不到连接复用，远端常驻进程是唯一能同时解决这三条的路。

## 目标与非目标

**目标（让远程项目像本地项目一样）**：目录树实时、文件预览可用、仓库自己的规矩（`AGENTS.md`）与技能进上下文、可上传本地 skill 到远端、长任务稳定可控、可选预览远端端口。

**非目标**：远端跑 Agent、远端会话存储、断线续跑；远端项目内新建笔记；远端 `dela` 校园命令；helper 内实现 PTY（终端继续 `ssh -tt`）；v1 只支持 Linux 远端（Windows 远端待决）。

## 两种模式与降级边界

| 模式        | 用途        | 说明                                                                        |
| ----------- | ----------- | --------------------------------------------------------------------------- |
| helper 通道 | 日常执行    | 上传校验、启动、`ssh -L` 隧道、握手、常驻；工具、目录树、@ 索引、预览都走它 |
| 一次性 ssh  | 引导 + 降级 | 上传与启动 helper 的手段；helper 不可用时承接全部远程能力                   |

**降级后不可用的能力**（必须在 UI 明说，不能含糊成「只是慢」）：目录树实时刷新、大文件按需片段读取（退化为整文件读取）、二进制上传下载、服务端哈希、`ls` 的精确 stat（退化为 10 秒缓存）、长任务的取消与状态查询（只能杀本地 ssh，远端进程可能继续跑）。**仍然可用**：七个工具、终端、@ 候选（一次性索引）、读写与编辑。

## 协议草案（v1）

**通道**：`ssh -L 127.0.0.1:<本地端口>:127.0.0.1:<helper端口>`；helper 只绑回环；请求 HTTP/JSON，流式用 SSE。**鉴权**：随机 token，`0600` 文件或环境变量传递，每请求带 `Authorization: Bearer`。

| 方法 | 路径                  | 用途                         | 关键字段                                                                         |
| ---- | --------------------- | ---------------------------- | -------------------------------------------------------------------------------- |
| GET  | `/v1/hello`           | 版本与能力协商               | `protocol`、`helperVersion`、`pid`、`platform`、`home`、`features[]`、`clientId` |
| POST | `/v1/fs/list`         | 列一层（带 stat）            | `path` → `entries[{name,dir,size,mtime,mode}]`                                   |
| POST | `/v1/fs/stat`         | 批量状态                     | `paths[]`                                                                        |
| POST | `/v1/fs/read`         | 片段读取                     | `path`、`offset`、`length` → 字节流                                              |
| PUT  | `/v1/fs/write`        | 原子写（临时文件 + `mv`）    | `path` + 内容                                                                    |
| POST | `/v1/fs/hash`         | 服务端 sha256                | `paths[]`                                                                        |
| POST | `/v1/exec`            | 起任务，SSE 流式输出         | `command`、`cwd`、`env`、`timeoutMs` → `{taskId}`                                |
| POST | `/v1/exec/:id/cancel` | 取消任务                     | —                                                                                |
| GET  | `/v1/tasks`           | 任务状态（含最近结束的任务） | → `[{taskId,state,exitCode,signal,startedAt}]`                                   |
| GET  | `/v1/watch`           | 目录事件（SSE）              | `paths[]` → `{type:'fs',path,kind}`；含 `overflow` 事件                          |
| GET  | `/v1/ports`           | 远端监听端口                 | → `[{port,address}]`                                                             |
| POST | `/v1/heartbeat`       | 客户端心跳                   | `clientId`                                                                       |
| POST | `/v1/shutdown`        | 显式停止                     | `clientId`                                                                       |

**任务模型（第一版核心）**

- 任务有 `taskId`；状态机：`running → exited(code,signal) | cancelled | timeout | lost`。
- **进程组**：helper 以新进程组启动命令（`Setpgid`），取消/超时对**整组**发 `SIGTERM`，宽限 5 秒后 `SIGKILL`。Go 的 `CommandContext` 只取消被启动的那个进程，不足以停掉构建工具的子进程。
- **超时**：由 helper 裁定（默认值可配），本机不再用 120 秒当权威。
- **客户端失联**：心跳中断后，helper 终止在跑的任务（宽限期可配），避免孤儿构建堆积。
- **输出**：按字节传（二进制安全），文本模式由客户端解码；单任务保留上限（例如 8 MB），超出丢弃并附 `…(已丢弃 N 字节)`；消费过慢时停止读取（背压），不无上限占内存。现状是 stderr 一直往内存里存，必须改。
- **结果区分**：`exitCode`（跑完了）／传输错误（通道断了）／**结果未知**（通道在任务中途断）三者分开。未知时不自动重放。

**心跳与生命周期**

- heartbeat 是**独立信号**，与是否有工具调用无关：Dela 每 30 秒对活跃连接发一次；helper 连续 **5 分钟**收不到心跳即退出（用户 2026-10-09 定）。长任务、watch 流、用户在思考都不会误判为空闲。
- 显式停止：Dela 退出、删除连接、用户手动「停止远端服务」时调用 `shutdown`。
- **helper 属于连接，不属于项目**：一条连接上的多个项目共用一个 helper；`hello` 带 `clientId`，多个窗口各自注册，**最后一个**用户离开或超时才真正退出，避免一个窗口关闭影响其他窗口/项目。
- 更正：helper 以 `setsid nohup` 启动后，**ssh 通道关闭它感知不到**，因此不存在「干净关闭 → 立即退出」的机制；靠显式 `shutdown` + 心跳超时。
- `--port 0` 由系统分配端口并把真实端口与 pid 写到 stdout 与 `~/.dela/run/<clientId>.*`；`--stop` 供手动清理；启动时清理旧版本目录（最多留两版）。

## 引导与恢复

| 步骤     | 做法                                                                            | 失败时                                             |
| -------- | ------------------------------------------------------------------------------- | -------------------------------------------------- |
| 1 探测   | 现有 `probeRemote` 扩展：`uname -s/-m`、`bash`、`node -v`（可选）               | 认证失败 → 报中文原因                              |
| 2 查缓存 | 远端 `~/.dela/helper/<版本>-<sha8>/dela-helper` 是否存在且哈希一致              | 不一致 → 重传                                      |
| 3 上传   | 现有 `writeFile`（`cat > tmp` + `mv -f`）+ `chmod 700` 与 `+x`；先算本地 sha256 | 只读 `$HOME`／磁盘满 → 换 `$TMPDIR` → 仍失败则降级 |
| 4 启动   | `setsid nohup … --port 0 --token-file …`，读 stdout 拿端口与 pid                | `noexec`／SELinux 拦截 → 降级并报明原因            |
| 5 转发   | `ssh -L …`（`ExitOnForwardFailure=yes`）                                        | 失败 → 降级                                        |
| 6 握手   | `GET /v1/hello` 校验协议与版本                                                  | 不匹配 → 重传该版本 → 仍不行则降级                 |
| 7 常驻   | 工具、目录树、@ 索引、预览走通道                                                | 通道断 → 重连一次 → 再失败降级                     |

**通道恢复与操作重试是两件事**：

- **可自动重试**：建立通道、握手、只读查询（`fs.list`/`fs.stat`/`fs.read`/`fs.hash`）。
- **不可自动重放**：`fs.write`、`exec` 等有副作用的操作。通道在任务中途断掉时，远端**可能已经执行**，自动再跑一次可能重复写入、重复提交、重复部署。此时标记为「结果未知」，把任务 id 与最后收到的输出交给用户，由用户决定是否重试。
- 若要做「重新查询任务状态」，必须先在协议里定义任务 id 的可见范围与状态保留时长（例如 helper 内保留最近 100 个任务、进程重启即失效）；第一版先不做跨连接续查。

## 远端文件身份（已实施 2026-10-09）

**当时的现状（已修）**：

- `renderer/navigation/remote-tree.ts` 用**纯远端路径**作目录清单缓存键、展开键与行 id（`listings[path]`、`id: child.path`），跨连接无区分。
- `main/workspace/api.ts#remoteProjectOf` 按路径前缀在**所有**远程项目里找第一个匹配。
- 两台服务器上都有 `/home/user/app`（或一台的 `/home` 与另一台的 `/home/user/app`）时会串：清单被覆盖、条目归属错、@ 候选混、行提示显示错连接。

**实际改法**：

- 远端条目身份 = **项目 id + 远端路径**：`shared/remotes.ts` 的 `remoteNodeId(projectId, path)` 生成、`parseRemoteNodeId` 解析（项目 id 是 UUID，与盘符冒号不会混淆）。
- `remote-tree.ts` 的清单缓存键、展开键、失败记录与行 id 全部换成该复合身份，并且**每个项目只从自己的根往下走**（归属不再依赖对远端路径的再次解释）。
- `remoteProjectOf` 先用项目 id 精确解析；裸远端路径只在唯一匹配时归属，多个项目都装得下时抛「同时属于多个项目，无法确定归属」，不猜。
- 远端子条目不进数据库（只活在组件状态与本次运行的索引里），**没有持久化迁移负担**。

**验收结果**：新增「同路径两台连接不串」的渲染端用例与两条主进程用例（改前 4 条失败）；全量单测 71 文件 538 通过；真机串行 8 文件 47 通过；`pnpm smoke:remote` 真窗口通过（@ 候选与远程终端照旧）。

**未做**：@ 候选的索引键仍是 `remoteJoin(项目根, 相对路径)`，只在同一项目内使用，暂无跨连接歧义；等预览阶段需要跨项目引用时再统一。

## 上下文与 skills

**撤回上一稿的承诺**：不再假设「不动现有路径处理」。已核对 SDK 的三处行为：

1. 技能列表进系统提示时用 `<location>${skill.filePath}</location>`，并告知模型「相对路径按 skill 目录解析，命令里用绝对路径」（`dist/core/skills.js`）。
2. `/skill:name` 展开时 `readFileSync(skill.filePath)` **本地直读**，展开块里同样带 `location` 与 `baseDir`（`dist/core/agent-session.js:1675`、`:1677`）。
3. 技能发现本身用本地 `readFileSync` 读 `SKILL.md`。

所以镜像到 Windows 后：**发现与展开能用**（本地有真实文件），但**模型看到的路径会被交给已被替换成远端读取的工具** —— 必须有一条路径映射。

**方案：上下文镜像 + 路径映射**

- 每个远程项目一个镜像根：`<userData>/remote-context/<remoteId>/<projectId>/`，同步 `AGENTS.md` 与三处 skills 的文本文件（不做全量镜像）。
- **映射规则**：所有远端工具入口先把「落在镜像根下的路径」前缀翻译成对应远端路径，再做现有的归一化（`remotePath`）；`read`/`write`/`edit`/`bash`/`grep`/`find`/`ls` 全部走同一函数。这样模型拿 `<location>` 里的镜像路径去读、去跑，落到远端仍是正确文件。
- **位置三分**要写清：本地镜像（发现用）、模型可见位置（`<location>`/`baseDir`，指向镜像，靠映射翻译）、脚本执行位置（远端真实路径）。
- `AGENTS.md`：用 SDK 的 `agentsFilesOverride` 注入远端内容（`path` 写远端路径），不需要镜像，也不依赖本地存在该文件。
- **校园 skills 在远程会话要摘掉**：现在远程分支仍传 `skillPaths: [builtinSkillsDirectory()]`，而内置技能正文教的是 `dela` 命令——远端没有。远程会话只加载镜像里的仓库/服务器技能。
- 刷新：会话开始时读一次；有 helper 时由 `watch` 事件刷新；无 helper 时在打开项目/手动刷新/每轮对话结束时读。

**三处远端 skill 位置与优先级**：`<仓库>/.agents/skills`（Pi 原生）＞ `<仓库>/.dela/skills`（Dela 专属，随仓库进 git）＞ 服务器 `~/.dela/skills`（同服务器所有项目共享）。

**上传（本地 → 远端）**：设置页技能列表加「上传到远端项目…」；目标 `<仓库>/.dela/skills/<名字>/`，含 `SKILL.md` 与附属文件；同名需确认覆盖；上传后立即刷新镜像。技能里的脚本在远端执行（用远端自己的 Node/Python），与 helper 语言无关。

**验收**：远端 `AGENTS.md` 的暗号能被远程会话引用；`/skill:name` 展开内容与远端文件一致；三处位置的技能都出现在列表并可触发；上传后远端文件逐字节一致且进 `git status`；映射单测覆盖「镜像路径 → 远端路径」与「普通远端路径不受影响」。

## 预览与传输

- `fs.read` 支持 `offset`/`length`：先取头部嗅探类型，再按需补齐；文本/代码只读预览、Markdown、图片、PDF 复用本地预览组件；远端文件点击不再是「下一阶段」提示。
- 大文件设单次与总量上限、可取消；不整篇进内存。
- 上传下载：`fs.write` + `fs.read`；「用系统默认程序打开」= 下载到临时目录后 `shell.openPath`，退出清理。
- **watch**：`fsnotify` 不递归，需逐层建立监听；NFS/FUSE 不保证事件；事件队列会溢出。因此必须配「溢出/错误 → 重扫该目录」与「窗口聚焦/每轮结束 → 轻量对账」，并在降级时明确不可用。

## 风险与未决

- **Go 工具链进入贡献者门槛**：缓解方式是预编译产物入库（`vendor/dela-helper/`），只有改 helper 才需要 Go。
- **受限环境**：`noexec`、SELinux、只读 `$HOME`、磁盘满；必须能检测并降级，安装目录可配。
- **并发断连原因未定位**：`sshd -T` 为默认 `maxstartups 10:30:100`（限制未认证连接），但我实测 12/30 条并发全部成功，没能复现；先前那几次失败按「偶发」记录，不再归因。
- **长任务语义是新面孔**：进程组终止、背压、结果未知三件事都容易做错，必须在 6.1 就有测试。
- **路径映射是新的静默风险点**：映射错会把远端命令指到错误文件；需要与 `remotePath` 同级的单测覆盖（镜像路径、普通远端路径、相对路径、含空格与中文的路径）。
- **arm64 未真机验证**；helper 资源占用未实测。
- **未决**：是否做 JS 扩展宿主；Windows 远端是否支持；远端 MCP 端口转发是否纳入；`fsnotify` 之外是否需要自建轮询兜底。

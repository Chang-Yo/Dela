# Agent 与工作区重构计划

日期：2026-09-29。状态：重构方向确定，尚未实施；具体依赖版本、接入兼容性与交互细节待阶段验证。

> **重要：文件与目录组织是本次重构的核心要求。**
>
> 本计划涉及 Agent Core 与工作区的大规模重构。必须主动按职责拆分文件、建立清晰的目录，精简实现并解除模块耦合，方便独立调试、定位问题和后续修改。不要把新增逻辑全部堆进一个文件，也不要继续让已有大文件承担多种职责。
>
> 执行核心、会话与持久化、上下文与压缩、业务工具、MCP/Skills 接入，以及工作台布局与界面，应按实际边界组织到相应目录，目录内再按具体职责拆文件。入口负责组装与调用，模块通过明确接口协作，避免跨目录随意读取内部状态或产生循环依赖；测试就近组织，便于单独验证。拆分时同步清理因迁移产生的重复实现和失效入口。
>
> 本轮不以“少建文件、优先挤进现有文件”为目标；原有简洁原则不能成为拒绝合理拆分的理由。单应用、单 package 继续保持，合理增加文件夹不等于拆成 monorepo，也不要求额外增加无用途的类或封装。以职责清晰、依赖明确、调试和修改方便作为组织质量的判断依据。

本文汇总本轮产品与架构讨论，作为后续 Agent、项目导航、标签和分屏重构的依据。与[技术规划](technical-plan.md)冲突的相关演进方向以本文为准；原文中的现有实现、数据保护和进程边界约束继续有效。本文不替代已完成的 [Markdown 编辑器计划](../plan.md)，也不代表以下能力已经交付。

## 1. 产品方向

Dela 以 Project 为持续工作的组织中心，以通用 Agent 为执行基座，通过业务工具深入连接课程、资料、邮件、日程和本地文档，并逐步接入 MCP 与 Skills。用户既可以委托 AI 推进任务，也可以直接阅读资料、记笔记和修改成果。

界面采用“项目与会话导航 + 统一标签工作台”：聊天、笔记、文件预览和修改审阅是平等的工作内容。用户通过标签与分屏决定工作重心，不再由首页和项目页分别规定“聊天为主”或“编辑为主”。

三个参照各有用途：

- Codex：借鉴项目下组织会话的方式，以及会话、一次请求、执行项之间的边界。
- VS Code：借鉴每组独立标签、拖拽分组、横纵分屏和局部工具栏。
- Pi：复用 Agent Core 的执行基础，接入 Dela 的模型服务、业务工具与上下文。

保留 Markdown 为笔记持久化正文，保留所见即所得编辑体验。编辑器承担用户创作、检查和接管 Agent 成果的职责；本轮不引入 Notion 数据库或自有块文档格式。

## 2. 重构要解决的问题

讨论时核查的主要限制如下；实施前需结合同期代码变更复核。

| 当前边界                                                            | 重构目标                                                         |
| ------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 项目主要通过会话 `scope` 分组，项目身份未作为完整执行上下文传入工具 | 项目明确提供工作背景、默认目标与资源范围                         |
| 当前会话选择与运行状态按 `scope` 耦合                               | 运行按会话与请求管理，切换视图不影响执行                         |
| 历史工具结果已保存，但模型上下文仍按固定消息条数截取正文            | 本轮引入按模型上下文预算触发的历史压缩，替代硬编码最近 12 条消息 |
| 编辑工具主要是带 revision 的整篇替换                                | 支持局部修改、差异呈现、版本冲突与恢复                           |
| 编辑布局固定为两个组，助手另占专用面板                              | 聊天与文档共用标签组，支持灵活双屏与三屏                         |
| 工具栏存在重复、低频操作，控件较抢眼                                | 精简常驻操作，减小视觉占位，按作用范围布置                       |

已有业务 API、资源引用、文件保存与版本检查、编辑器和聊天组件继续作为基础。按实际耦合点调整，不为本轮重构连带重写校园业务。

## 3. 共同的数据与状态边界

| 对象       | 职责与关系                                               |
| ---------- | -------------------------------------------------------- |
| Project    | 工作主题、背景、关联资源和能力配置；不要求是 Git 仓库    |
| Session    | 归属项目或无项目的通用对话，保存独立历史                 |
| Run        | 一次用户请求及其后续执行，记录状态、工具调用、结果和中断 |
| 文档与资源 | 由项目组织或关联，具有稳定引用；可写文档具有版本         |
| 标签与分屏 | 展示会话或资源，保存布局、焦点与阅读位置，不拥有执行任务 |

一个项目可以有多个会话；会话可以引用同一份文档。成果独立于产生它的聊天，关闭标签不删除会话或文件，删除会话不连带删除项目成果。

分开管理三类状态：项目、会话和文件等持久数据；正在执行的 Run；标签、光标、滚动和布局等视图状态。切换项目或关闭聊天标签不隐式停止任务，停止执行使用独立入口。应用退出后不承诺自动续跑；重新进入时应能识别中断并由用户继续，避免重复执行已完成的写入。

同一文档在多个组打开时共享正文与版本，视图位置可以不同；同一会话的多个入口共享会话状态，不能因打开视图而启动重复 Agent。数据与执行仍通过有限的 preload API 访问，renderer 不持有凭据或直接访问数据库。

## 4. 工作台与交互方向

### 4.1 项目与会话导航

最左侧按项目展开会话，优先呈现近期会话，通过“显示更多”或会话列表访问历史。会话显示必要的运行、完成或等待输入状态，用户离开聊天后仍能发现需要处理的结果。

保留无项目的通用聊天入口；从项目中新建的会话自动归属该项目。项目文件应有独立且明确的浏览入口，记笔记不必先创建或进入聊天。邮箱、课程等业务入口继续保留，不要求用户把每项业务活动都建成项目。

建议首轮按项目保存各自的打开标签与布局，切换项目时恢复工作现场。跨项目标签是否混排、文件导航的具体位置属于待确认的交互细节，不在数据模型中把会话归属绑定到当前可见项目。

### 4.2 统一标签与灵活分屏

每个工作组拥有自己的扁平标签栏和活动标签。聊天、笔记、预览、修改审阅采用相同的打开、激活、移动和关闭规则，以图标区分内容类型。

**最终实现像VSCode一样的灵活度**

- 单组可呈现完整聊天或完整编辑器；不设两套独立的聊天模式与编辑模式。
- 标签可在组内排序、跨组移动，并通过边缘拖放或分屏按钮创建横向、纵向分组。
- 支持双屏、三屏及左右与上下组合；组间尺寸可拖拽调整。
- 点击已打开的条目优先定位已有标签；显式并排打开时再创建另一视图。
- 合并布局应保留打开内容；最大化当前组后可以恢复原布局。
- 根据实际可用区域处理窄屏，优先收纳次要控件，不将多个组压缩到无法阅读。

布局用分割节点与标签组表达，避免继续叠加“第三栏”“助手特例”等固定分支。实现保持最小规模，先检查成熟分屏与拖拽方案是否适合现有 React/Electron 环境，不预建通用 IDE 扩展系统。

拖动、切换与布局恢复应保留输入草稿、光标、撤销历史和滚动位置。动画保持视线稳定，不因工具运行或新成果出现自动改变分屏、抢占焦点。

### 4.3 功能键：简洁、明确、高频

本轮应审查现有操作的实际用途，而不是把全部按钮搬进新的工具栏。

- 常驻按钮优先保留当前任务的高频操作；低频操作进入菜单或上下文入口，已被自动行为取代的重复入口移除。
- 笔记已有自动保存，正常状态不再常驻“保存”按钮。保存状态低干扰展示；失败或冲突时提供明确提示、重试或恢复入口，不能因移除按钮而隐藏问题。
- 缩小按钮、图标、行高和留白的视觉占位，优先复用统一尺寸 token；具体尺寸在原型审阅后确定，不逐处添加任意数值。
- 视觉紧凑不牺牲点击区域、键盘操作、聚焦反馈和可读性。常见动作使用贴切图标并提供提示，含义不清的动作保留文字。
- 入口尽量靠近作用对象；同一动作避免在标题栏、标签栏和内容区重复常驻。折叠后仍需保留可发现的展开入口。

| 作用范围       | 适合放置的操作                           |
| -------------- | ---------------------------------------- |
| 窗口与导航     | 全局搜索、导航开关、整体布局入口         |
| 当前工作组     | 分屏、最大化、组操作菜单                 |
| 当前内容       | 笔记格式与源码切换、PDF 导航、修改审阅等 |
| 聊天输入与执行 | 模型选择、附加上下文、发送与停止         |

各组的常用操作保持稳定位置。焦点从聊天转到笔记时，不让全局工具栏大幅换位；空间不足时先收纳次要功能。

### 4.4 设置分类与入口同步重构

设置页面随工作台和 Agent 一起调整，以 Dela 现有“设置分类侧栏 + 右侧内容页”为基础。应用主导航与设置分类已经各有职责，设置内部先保持一层可直接点击的分类，不增加抽象的导航分组或额外导航列。参考 ChatGPT app 的分类命名、搜索和插件管理方式，具体入口按 Dela 的实际使用场景组织。

当前设置包含通用、数据与服务、模型服务、插件、外观、关于。保留含义清楚的名称与熟悉的入口，重点拆清“数据与服务”中校园连接和工作目录的归属。“插件”目前只有自定义 `/` 提示词指令，后续在该页加入 MCP 与 Skills 的管理，不能把已有指令功能当成协议支持已经完成。

以下是用于后续原型审阅的分类建议，不作为已经确认的最终导航：

| 设置侧栏入口 | 用户在这里调整什么                               | 与当前界面的关系                         |
| ------------ | ------------------------------------------------ | ---------------------------------------- |
| 通用         | 开机自启动等应用行为，快捷键说明入口             | 保留；少量说明与偏好不单独拆页           |
| 外观         | 主题、字号、页面缩放、应用图标                   | 保留                                     |
| 通知         | 校园消息与 Agent 任务的提醒偏好、暂停通知        | 随相关通知选项补充，和通知中心共用状态   |
| 工作区       | 工作目录、项目与标签恢复、笔记编辑偏好、布局重置 | 新增，接收原“数据与服务”中的工作目录     |
| 模型服务     | 提供商、API 配置、连接检测、默认模型与推理强度   | 保留现有名称和配置入口                   |
| 连接         | Canvas、邮箱、教务、水源的登录、授权与同步状态   | 由“数据与服务”收敛，专门管理业务服务连接 |
| 插件         | Skills、MCP、自定义指令的添加、启停和配置        | 扩展现有页面，内部按类型切换             |
| 关于         | 版本、项目和帮助信息                             | 保留                                     |

“连接”处理已有业务服务的账户与同步，“插件”处理为 Agent 增加的扩展能力；两者不合并成含义宽泛的“能力与连接”。插件页中的 Skills、MCP、自定义指令是不同内容类型，不要求现有指令迁移成 Skill，也不需要先建设插件市场。若扩展使用已有服务授权，应引用同一连接，不重复配置凭据。

少量选项留在对应页面内，不为“指令与行为”“数据与支持”等抽象概念另设导航入口。邮件保留期归邮箱连接详情，工作文件位置归工作区，模型上下文外发说明归模型服务及引用入口。以后某类设置形成足够独立的使用需求，再考虑拆页。

本轮优先补齐的设置与入口：

- **查找与直达**：设置内支持按分类、选项名称及常见关键词搜索；保留应用全局搜索入口。模型未配置、连接失效、能力缺少依赖时，直接跳转到对应项，而不是只打开设置首页。
- **工作现场偏好**：提供启动时恢复上次项目与标签的选择、默认笔记编辑方式和当前项目布局重置。分屏比例、标签顺序等由直接操作自动记忆，不为每个布局细节再增加设置；恢复视图不代表自动恢复 Agent 执行。
- **任务通知**：允许选择 Agent 完成、失败、等待用户输入等事件是否提醒。关闭系统提醒不丢失执行记录和侧栏状态；已有通知暂停行为与新设置使用同一份状态，不出现互相矛盾的开关。
- **能力管理**：随 MCP/Skills 接入补齐添加或导入、配置或来源查看、启停、连接检测或依赖状态、移除入口。未实现的协议或执行环境不展示可用开关，依赖缺失时说明原因。
- **行为与数据控制**：随文档协作在工作区设置中补齐默认修改应用/审阅策略；保留策略和清理说明放在对应业务或存储设置附近。备份、导出、缓存清理等新增操作须有对应实现并明确数据范围，不先放置无实际行为的按钮。

全局设置提供默认值，项目设置只覆盖有实际项目差异的背景、指令、资源范围和能力启用。标明当前值来自全局还是项目，并提供“恢复继承”；凭据由应用统一管理，项目引用连接，不复制密钥。会话中的临时模型选择和本轮引用不应悄悄改写全局默认，项目偏好也不能扩大宿主授权的权限。

全局设置继续从应用导航中的“设置”进入，项目级设置从项目菜单进入，相关页面提供直达链接，复用同一设置状态。保留现有分类侧栏和内容页结构，先优化分类、选项和紧凑程度；未来如需接入统一标签工作台，再单独确定承载方式。打开设置不应丢失工作现场或停止任务。

简单偏好即时保存，反馈保持低干扰；凭据、服务地址等需要整体校验的表单保留明确的验证与提交动作，不把“精简保存按钮”机械应用到所有表单。设置应说明作用范围和生效时机，失败时保留输入并提供重试。未来 sandbox 设置随实际执行能力落地后加入，不提前提供绕过隔离的开关。

分类迁移必须同步全局搜索、快捷入口、错误引导和旧设置定位请求，保留已有偏好与自定义指令。实施时同步设置接口文档；本计划中的新增选项不代表当前设置 API 已支持。

## 5. Agent Harness 方向

### 5.1 复用 Pi Core，Dela 管理会话与业务

技术路线以复用 Pi Agent Core 为基线，借鉴 Codex 的会话管理。先进行最小接入验证，再确定精确版本与替换范围；不直接搬入 Pi 的终端界面，也不默认接入完整 Codex 后端。

| 部分                     | 职责                                                     |
| ------------------------ | -------------------------------------------------------- |
| Pi Core 及其实际所需依赖 | 模型交互、工具循环、流式事件、取消与运行中输入等执行基础 |
| Dela 会话与运行          | 项目归属、持久历史、执行状态、继续、中断与归档           |
| Dela 上下文组织          | 项目背景、历史选择、引用与选区、Skills、上下文预算       |
| Dela 能力入口            | 内置业务工具、MCP 接入、输入校验、资源范围与结果         |
| Dela 工作台              | 订阅会话和资源变化，呈现聊天、编辑、预览与审阅           |

只保留一套持久会话事实来源，明确 Pi 内存状态与 Dela 存储的衔接。统一 Dela 的 `Session → Run → 执行项` 语义，不直接混用上游对 turn 的不同定义。

Run 携带会话、项目身份和取消信号；执行记录有明确状态与结果。工具只依赖执行上下文和业务能力，不依赖聊天所在面板。新工具接入应主要改变能力定义和对应实现，避免反复改写模型循环与页面。

最小验证覆盖现有 OpenAI 兼容服务的流式、工具调用、停止和错误路径，以及历史持久化后继续工作。Pi Core 并不自动等于完整的会话管理、Skills 加载或 MCP 支持，这些能力逐项确定复用位置。若关键兼容性不成立，先记录阻碍并重新评估，不静默改回另一条技术路线。2026-09-29 最小接入验证已完成（依赖 0.87.1、本地 mock 实测七类路径全部通过），结论与限制清单见 [pi-integration-report.md](refactor/pi-integration-report.md)：可以替换自研循环，无关键不成立项；真实提供商与 Electron 打包环境实测留待接入阶段。

### 5.2 全业务工具盘点与接口重设计

工具重构覆盖全部业务领域，edit 只是其中一个重点。不能把现有工具原样迁入 Pi 就视为完成，也不能把应用已有业务 API 等同于 Agent 已具备对应能力。第一阶段先形成“用户任务—业务能力—现有工具—缺口—处理决定”的清单，逐项决定保留、调整、合并、拆分或补充；未开放的能力明确列出原因。

讨论时核查的重点如下，实施前复核具体代码：

| 领域         | 当前覆盖与限制                                                                                           | 设计重点                                                                                                        |
| ------------ | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 水源         | 业务 API 已有搜索、主题、楼层等能力，显式引用可读取水源正文；Agent 工具列表和通用资源引用尚未覆盖水源    | 补齐发现、搜索、主题与楼层分页读取、可引用结果的闭环；回复、私信等写入单独评估，不随只读接入自动开放            |
| 课表与日程   | 已有按时间范围查询课程与个人事件，返回上海时区及不完整警告；工具侧缺少完整的学期发现、同步状态与刷新路径 | 明确学期、日期范围、时区和课程/个人事件筛选，区分没有课程与数据尚未同步；个人事件和 Canvas 截止事项保持来源语义 |
| Canvas       | 已有课程查找、资料搜索、同步与作业查询；状态分散在不同结果中，课程列表与内容同步含义不同                 | 分清凭据配置、实际可访问性、课程/资料/作业的同步状态与覆盖范围，形成状态诊断、检索、读取、按需刷新闭环          |
| TODO         | 查询混合个人待办与 Canvas 作业，作业查询又提供另一入口                                                   | 明确综合查询与领域查询的分工，统一筛选和状态表达，保留个人完成状态与作业提交状态的区别                          |
| 邮件与附件   | 已有缓存搜索、正文读取和草稿准备；附件正文目前需要先导入项目                                             | 评估附件直接读取和资料流转的缺口，明确搜索范围、缓存新鲜度及草稿/发送边界                                       |
| 工作区与网页 | 已有名称检索、资源读取、文件组织、整篇笔记写入与联网工具                                                 | 补齐正文定位、局部修改、来源引用与结果可继续读取的能力，保持跨业务资源传递一致                                  |

这里的“状态”需要拆开定义。例如 Canvas 当前 `connected` 由本地是否保存 token 得出，不能等同于在线验证成功；课表无结果也不能直接解释成当天没有课。状态查询应返回完成当前任务所需的简明诊断，而非把供 UI 使用的整个 state 对象交给模型。

通用工具负责发现、搜索、读取资源和编辑文档；业务工具保留邮件、作业、日程等领域语义；跨业务流程由 Agent 配合 Skill 组织。

例如“结合课件和老师邮件制作复习计划”应组合课程检索、邮件检索、资源读取、文档编辑和待办工具。既不为每种任务增加一个固定流程大工具，也不把所有领域压成一个任意操作的通用入口。

统一资源引用、来源、新鲜度、分页、版本和错误表达。工具结果应能携带文本、结构化数据及必要的媒体或成果引用，模型与 UI 按各自需要使用。大结果保留可重新读取的依据，避免单纯截断后丢失后续工作所需的信息。

接口设计遵循以下共同约定，具体名称与 schema 在盘点后确定：

- **动作含义稳定**：区分状态、列表、搜索、读取、刷新和写入。同类动作采用一致的命名和参数语义；名称应体现业务范围，避免名称看似通用而实际只支持 Canvas 等单一来源。
- **输入容易构造**：时间、时区、日期区间边界、学期、资源 ID、分页和筛选采用共同约定。只要求任务必需参数，默认值来自明确上下文；查询课表不应依赖模型反复猜测当前学期或手算本地日期的 UTC 边界。
- **结果可以衔接**：搜索返回的引用能直接传给读取工具；主题能继续读取楼层，附件能进入读取或文件流转。统一分页与续读语义，底层远端 cursor 和本地 offset 可以不同，不为表面一致性伪造总数或分页能力。
- **覆盖范围可判断**：结果区分缓存与实时、完整与部分、空结果与未连接/未同步/失败；统一新鲜度和警告信息的表达。刷新目标与查询目标一致，是否自动刷新必须明确，不能悄悄启动全量同步。
- **失败可以恢复**：除输入错误外，区分未配置、授权失效、资源不存在、版本冲突、限流等真实边界，并提供可执行的后续方向。部分成功保留已取得的结果，不能用统一“操作失败”掩盖所有情况。
- **副作用可识别**：明确只读、刷新、本地修改和外部发布；重试、取消与已完成操作的语义清楚。沿用邮件备稿和不提交作业等现有边界，新增写入按真实需求单独设计。

统一的是契约与使用习惯，不强行把所有工具压成同一个结果对象或参数众多的万能入口。可参考 MCP 的输入/输出 schema、结构化结果与错误表达；协议元数据不能替代宿主实际的权限检查。工具按领域拆分目录和实现，复用已有业务函数，通过共同的薄契约进入执行循环，避免继续扩充单个 `tools.ts`。

能力启用、模型可发现的工具、执行权限分别处理。内置工具继续复用业务 API；已授权的能力按项目和任务需要加载。宿主在执行时检查资源范围，不能只依赖提示词或模型提供的项目 ID。

验收围绕任务链而非工具数量：例如“查询下周课程并识别缺失同步”“判断 Canvas 哪些课程资料或作业信息需要更新”“搜索水源讨论并读取后续楼层，再整理成项目笔记”。重点验证工具选择是否清楚、结果能否接续、数据不完整时是否如实说明。edit 的局部修改闭环与这些领域任务共同验收。

### 5.3 MCP、Skills 与后续执行环境

- MCP 作为外部能力入口，按协议处理工具、资源及提示模板。先验证具体服务器与实际需要的能力，明确支持范围；不要求内部 API 先全部改成 MCP 服务。
- Skills 负责描述适用场景、工作步骤及辅助资源。先发现名称与描述，命中任务后读取正文，再按需加载引用文件，避免把所有 Skill 全文常驻上下文。
- 能力可启停，连接失败或依赖缺失应明确呈现。关闭能力后保留历史结果与来源，后续调用按当前可用性处理。
- 本轮不以建设通用插件市场为前提。MCP、Skills 的接入与任意第三方代码插件加载分别评估。

未来加入通用命令或脚本执行时，以实际 sandbox 为前提，设计文件、网络、进程和资源限制，尤其验证 Windows 上的可行方案。工作目录限制和提示词不等于隔离。业务凭据继续由宿主管理，不默认交给脚本。

脚本执行不作为首阶段交付前提。能读取 `SKILL.md` 不代表能执行所有社区 Skill；依赖 Python、Shell 或其他程序的能力需在执行环境可用后单独验证。

## 6. 上下文与文档协作

### 6.1 上下文属于任务，不随焦点漂移

本次模型上下文由项目背景与资源索引、本会话有效历史、明确引用与选区、按需读取的资料、已激活 Skill 组成。不默认注入项目全部文件，也不自动混入同项目其他会话的完整历史。

上下文压缩是本轮重构的明确交付项，替代硬编码“最近 12 条消息”的截取方式，也不改成让用户配置保留条数。持久历史完整保留，发送给模型的上下文由历史摘要、近期完整交互和当前任务资料组成；预算充足时保留有效历史，不因达到固定条数而丢弃。

- **按预算触发**：依据当前模型的上下文窗口评估输入占用，计入指令、工具定义、引用资料和媒体，并为输出及后续工具交互预留空间，在接近预算时压缩较早历史。每次模型请求前检查，多轮工具执行和模型切换也适用；窗口大小来源与 token 估算方式在接入阶段验证，未知时明确采用保守预算，不根据模型名称猜测。
- **保留任务连续性**：摘要保存用户目标与约束、已作出的决定、已完成操作及关键结果、未完成事项、资源引用与版本。当前请求及近期必要的工具调用/结果保持完整关联；未完成的调用不能被压缩成已完成，也不能因压缩而重放已有写入。
- **摘要可追溯**：摘要记录所覆盖的历史范围，与之后的新消息共同组成上下文；原始记录仍可检索或重新读取。压缩不删除聊天记录，不把外部资料中的指令提升为用户要求，不把摘要当成资源最新状态。
- **失败可恢复**：压缩成功后再替换模型上下文。失败保留原始历史并明确反馈；如果已无法容纳下一次请求，允许重试或减少本轮资料，不静默退回固定条数截断。单份大资料仍需分页或按需读取，不能指望历史摘要解决全部输入超限。

优先评估 Pi 生态中可复用的压缩实现与上下文入口，明确其与 Dela 持久历史的衔接，不把引入 Agent Core 等同于已经具备自动压缩。界面以低干扰方式显示压缩进行或失败状态；具体预算与触发余量在验证中确定，不在本计划中写死统一阈值。

从编辑器发起请求时记录当时的资源、选区和版本；切换标签不改变运行中任务的目标。用户需要改变任务时，应通过明确的追加指令或上下文操作完成。项目范围、显式引用和选区在界面上应可理解。

### 6.2 人与 Agent 操作同一份文档

先完善 Markdown 局部编辑：基于明确版本提交一组文本修改，校验匹配与重叠，一次提交返回新版本、差异和定位依据。沿用现有保存与 revision 机制，避免同时维护 Markdown 和另一套正文事实来源。

编辑器草稿与磁盘内容可能不同。初期从编辑器发起修改时，可先等待当前草稿保存成功，明确 Agent 所依据的版本；执行期间用户继续输入，不能被后到的 Agent 结果覆盖。版本变化后提供重读或冲突审阅，保留用户草稿。

修改应可查看差异并有恢复依据；恢复同样检查后续版本。明确区分“建议修改”“已应用修改”“应用失败”，避免聊天文本声称完成而文档尚未变化。已明确授权的写入不必逐次弹窗确认，具体自动应用与审阅策略在文档协作阶段细化。

文件改动通过资源变化通知相关视图，逐步替代仅在聊天结束后整体刷新的方式。关闭编辑标签不妨碍 Agent 操作已授权资源，打开标签后能看到实际结果。

## 7. 实施阶段与完成依据

| 阶段                   | 主要工作                                                             | 阶段完成依据                                                                        |
| ---------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 一：边界与 Pi 接入验证 | 确定共同状态边界；盘点全业务工具覆盖与接口契约；最小接入 Pi Core     | 形成工具缺口与迁移清单；现有模型服务通过真实工具调用、流式、中断和历史续接验证      |
| 二：执行与业务闭环     | 按领域重设计工具并补齐关键缺口，落地上下文压缩与文档版本协作         | 水源、课表、Canvas 等任务链可完成且状态可判断；压缩可续接，文档冲突不覆盖草稿       |
| 三：统一工作台         | 项目会话导航、混合标签、灵活分屏、布局恢复、功能键精简及设置分类迁移 | 聊天、笔记、预览可自由组合成单屏、双屏、三屏；设置可搜索直达，旧偏好保留            |
| 四：可插拔能力         | MCP 与 Skills 按需接入和启停，补齐能力设置与项目覆盖，完善跨业务组合 | 用实际外部能力与 Skill 完成跨业务任务，断连和缺失依赖有明确反馈，设置范围与执行一致 |

工作台原型可在前两阶段用于审阅，但正式迁移遵循共同状态边界。每阶段形成可使用的闭环，不要求全部完成后一次替换。

上下文压缩验证覆盖长对话、多轮大工具结果、模型上下文窗口变小、压缩失败与重启后续接。检查早期用户约束、已完成写入和未完成事项能否正确保留，工具调用关系是否完整，原始历史是否仍可找回；不以“请求未超限”作为唯一完成依据。

设置重构随相关能力分阶段交付：分类、搜索与现有选项迁移进入工作台阶段；任务通知、修改策略、MCP/Skills 管理分别随对应执行能力验证。检查从错误提示直达设置、配置后回到原任务、全局与项目继承、生效时机和失败反馈，避免只完成页面分类而行为仍沿用旧入口。

选型优先参考官方文档和成熟开源实现；保持单应用、单 package，按文首工程组织要求主动拆分文件与目录、精简和解耦，不增加无真实用途的抽象层。各阶段同时检查目录归属、模块依赖和可独立调试性，避免功能迁移后仍由单个大文件集中承担。依赖采用精确版本并维护锁文件。

迁移保留既有会话、项目、文件与可恢复数据，尽可能继承旧双栏布局；新增信息无法从旧数据恢复时明确标记，不能补造历史上下文。存储迁移先备份，运行和写入路径切换时避免新旧实现同时执行同一请求。

验证集中在相关阶段完成后进行，重点覆盖真实工作流程：纯聊天、纯笔记、聊天与笔记并排、课件与笔记及聊天三屏、运行中切换视图、自动保存失败、并发编辑冲突、重启后继续会话。涉及依赖、构建或原生能力时按项目约定验证构建、smoke 和打包启动。动画、拖拽过渡与视线稳定性由用户实机审阅，不用 Playwright 或自写多帧探针代替。

## 8. 暂不定死的事项与范围

方向已确定：项目下组织会话；聊天和文档共用标签组；支持灵活三分屏；工具栏高频、紧凑、低干扰；设置基于现有分类侧栏优化归属并补齐实际所需选项；复用 Pi Core 并借鉴 Codex 会话管理；业务工具可组合；接入 MCP 与 Skills；未来命令执行考虑 sandbox。

实施前按阶段确认以下事项：

- 每项目布局与跨项目混排的最终交互，以及项目文件导航的位置。
- Pi 的具体版本、现有模型服务兼容性与持久历史衔接方式。
- 分屏与拖拽实现的复用方案、紧凑控件的尺寸和窄屏行为。
- 设置分类的最终命名与承载形式、项目覆盖项及新增选项的默认行为。
- 文档修改自动应用、差异审阅和恢复的具体体验。
- 首批 MCP 服务器、Skill 的支持范围，以及未来 sandbox 方案。

本轮不扩展为完整 IDE、Notion 数据库、多用户协作、通用插件市场、多 Agent 协作或无人值守后台自治。接入 Pi 不自动改变这些产品范围。

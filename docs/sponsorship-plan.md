# Dela 在线赞助协作计划书

日期：2026-10-07。计划版本：0.1。接口草案：v1-draft-1。

面向：ECS 后端与赞助网页开发 AI（下称 ECS AI）、Dela 桌面端开发 AI（下称 Dela AI）。

状态：仅完成规划，未开发、未部署、未验证真实支付。用户已接受跳转爱发电收款；本文其余产品细节为建议基线，涉及未决事项时按第 3 节处理，不能把建议写成已获用户确认。

## 1. 目标与边界

用户在爱发电完成赞助，通过自己的爱发电身份提交或修改昵称、头像，选择公开后出现在 Dela 关于页。名单更新不再要求发布 Dela 新版本。

- 爱发电负责收款；ECS 核实订单、关联身份、保存资料并发布公开名单。
- Dela 只读取公开名单，在系统浏览器打开赞助网页；不接触支付密钥、爱发电登录态、订单明细。
- 自定义资料、付款状态及资料管理均放在网页，避免浏览器向桌面传递授权凭据，不新增桌面深链回调。
- 不建设 Dela 通用账号、云同步、积分、订阅权益、金额排行榜或多支付渠道抽象。
- ECS 建议独立仓库、单进程应用；Dela 保持单应用、单 package，不增加 monorepo 子包。
- 当前 Author 信息保留本地配置；Sponsors 改为线上数据。已有赞助者经所有者核实公开意愿后人工迁入，不能冒充已验证爱发电订单。

成功标准：经核实的真实付款与授权身份正确关联；用户可自行维护公开资料；Dela 刷新后显示最新名单；重复通知不产生重复记录；离线不影响应用其他功能。

## 2. 已知事实与待验证能力

依据 2026-10-07 查阅的官方文档：

- [爱发电 API 与 Webhook](https://guide.afdian.com/creator/developer)：可查询订单、赞助者，赞助者包含昵称和头像；通知可能重复或不及时。订单成功状态为 `2`；实际付款应看 `total_amount`，不能将 `show_amount` 或累计展示金额当作实付。
- 同一文档描述的是服务器请求 API 的签名，不能推断入站 Webhook 有同样的验签机制。实现前再次核对最新文档；在没有明确可验证的通知签名时，将通知仅作为查单线索，以服务端 API 查询结果为准。
- [爱发电 OAuth](https://guide.afdian.com/creator/oauth2)：通过官方分配的 clientID/clientSecret 授权，在服务器交换 code 获取用户标识；使用 HTTPS 和 state 校验。

尚未验证：账号 API 权限、OAuth 申请可用性、OAuth 标识与订单标识的实际对应关系、接口限流、付款到可查询的延迟、退款/撤销的查询与通知行为、付款后自动返回能力。平台文档存在不代表本账号已具备权限。

## 3. 开工前输入与决策

ECS AI 收集并在交接记录中登记以下非敏感结果；密钥由所有者通过部署环境提供，不粘贴到计划书、聊天、提交或日志中。

| 输入或决策 | 负责人 | 对进度的影响 |
| --- | --- | --- |
| ECS 仓库、操作系统、现有反向代理和可用部署方式 | 所有者提供，ECS AI 核实 | 可先开发，本项决定部署方式；不得影响已有服务 |
| 正式/联调域名、HTTPS、所在地适用的备案与平台接入要求 | 所有者与 ECS AI | 阻塞公网正式部署，不阻塞本地桩开发 |
| 爱发电创作者页、API 可用性及 Dela 对应赞助方案范围 | 所有者与 ECS AI | 阻塞真实订单核实；不能把其他项目订单计入 |
| OAuth 申请与用户标识匹配验证 | ECS AI | 阻塞自动认领和资料编辑上线 |
| 自动公开后可下架，还是先人工审核 | 所有者决定 | 建议自动公开；必须在开放用户提交前确定 |
| 已有赞助者的迁移资料与公开意愿 | 所有者 | 可后续迁移，不阻塞接口实现 |

昵称头像由用户自行提供，公开需主动选择，默认不公开。建议不展示金额、同人只显示一次、按首次取得展示资格时间倒序，同时间按公开 ID 排序；这些建议在 M0 记录确认结果。

OAuth 不可用时，不允许凭订单号、付款截图或自报昵称自动认领。可以另经用户选择上线人工核验的过渡版，但必须标注尚未完成自助身份关联；不能默默降低完整目标。

## 4. 用户流程与状态

1. Dela 点击赞赏，在系统浏览器打开固定赞助页面。
2. 网页说明公开范围，用户爱发电授权后编辑昵称、头像和公开选择。
3. 网页在新标签打开爱发电赞助页，原页面保留付款状态。
4. 用户付款后回到原页面；网页有限轮询自己的状态，也提供手动检查入口。
5. ECS 查单成功并关联身份后，满足发布条件即更新公开名单。
6. 用户返回 Dela，关于页可见时刷新，或手动刷新名单。Dela 不显示个人到账状态，因为桌面不持有网页身份。
7. 用户再次通过网页授权，可修改资料、取消公开。退款、争议或不当内容由后台机制纠正。

分开保存付款事实与资料状态。建议资料状态为草稿、公开、用户撤回、管理员隐藏；管理员隐藏不能被下一次同步或用户再次保存自动解除。没有已核实付款、没有公开同意、资料不完整时不得上榜。

不依赖平台自动跳回网站。付款通知、查单和客户端刷新都有延迟，界面使用“等待付款确认”，不能将超时等同支付失败。实时性作为联调观测结果，不承诺绝对秒到。

## 6. 跨端接口草案

本节是 ECS 与 Dela 的共同契约草案，M0 双方评审后冻结。路径和字段不允许单方修改。示例数据仅为虚构夹具，不能进入正式公开名单。

### 6.1 环境地址

- `SUPPORT_ORIGIN`：所有者确定的 HTTPS origin；桌面构建显式配置非敏感地址，不自动加载仓库 `.env`。
- 网页入口：`GET /support`。资料管理也从此进入，身份会话只在浏览器内。
- 公开名单：`GET /api/v1/sponsors`，不要求登录、不接受爱发电凭据。
- 头像：同 origin 的 `/media/avatars/…`；API 只返回相对路径，不允许远端数据提供任意协议或跨域图片地址。

### 6.2 名单响应

```json
{
  "schemaVersion": 1,
  "revision": "opaque-revision-001",
  "updatedAt": "2026-10-07T08:00:00Z",
  "sponsors": [
    {
      "id": "public-id-001",
      "name": "示例赞助者",
      "avatarPath": "/media/avatars/example-v1.webp"
    }
  ]
}
```

- `id` 为稳定且不暴露爱发电用户标识的公开 ID，重复付款和资料修改不得改变它。
- `name` 为纯文本；`avatarPath` 可为 `null`，客户端显示默认头像。
- `revision` 为公开名单版本，内容、顺序或可见性变化时更新；客户端只比较相等性，不解析格式。
- `updatedAt` 为该版本发布时间，UTC RFC 3339；不是客户端请求时间，也不是个人付款时间。
- 数组由服务端排好序，v1 返回完整公开名单，不偷偷截断。规模导致需要分页时，另行评审兼容方案。
- 未知附加字段允许忽略；已定义字段缺失、类型错误、重复 ID 或不支持的 schemaVersion 均视为无效响应，保留旧缓存。
- `200` 且空数组是有效的最新名单，必须清除旧名单；错误或无效响应不得伪装成空名单。
- 返回 `ETag`，客户端用 `If-None-Match`；`304` 保留现有数据并更新本地成功检查时间。无对应缓存时不得使用孤立 ETag。
- 建议 `Cache-Control: no-cache`，每次联网刷新重新验证，避免中间缓存长期保留已撤回资料。
- `429` 携带 `Retry-After`；`5xx` 表示暂不可用。错误体统一为 `{"error":{"code":"UNAVAILABLE","message":"暂时无法获取赞助名单"}}`，不返回内部异常或订单信息。

公共接口永不返回订单号、付款金额、平台用户 ID、邮箱、授权令牌、未公开资料或管理员状态。客户端不使用服务器下发的 HTML，也不将昵称解释为 Markdown。

### 6.3 数值边界与夹具

M0 由 ECS AI 提出并与 Dela AI 冻结昵称长度、图片输入大小/像素限制、名单响应大小上限、请求超时、轮询退避、缓存最大保留期和限流参数。必须在契约交接中给出具体值及理由，不能让两端分别猜测，也不要为了文档初稿随意设定限制。

ECS AI 维护一套脱敏 JSON/HTTP 夹具，Dela AI 固定消费同一契约修订版：正常名单、空名单、无头像、昵称特殊字符、重复 ID、非法头像路径、未知字段、无效响应、304、429、503、撤回后新版本。头像更换采用新路径，避免旧图缓存影响展示。

### 6.4 ECS 内部接口

OAuth 发起/回调、本人资料读写与上传、本人付款状态、Webhook、管理员操作均由 ECS AI 设计，Dela 不依赖其具体路径。本人接口使用安全会话和 CSRF 防护，OAuth state 绑定会话并一次性消费；服务端交换 code。不以客户端传来的用户 ID 决定资料归属。

## 7. ECS AI 实施清单

- 优先复用现有部署设施；新服务建议 Node.js/TypeScript、SQLite、持久化头像目录。先查官方文档和维护中的成熟组件，不手写 OAuth 协议框架或图像解码器，不预建通用支付框架。
- 以订单号唯一约束实现幂等；金额按平台精度解析为最小货币单位，避免浮点比较。验证收款账号、方案范围、成功状态、实付金额和付款人。
- Webhook 收到后先可靠记录待处理线索，再确认接收；失败可重试。使用同一数据库的待处理状态即可，无需单独消息队列。限流并合并查单请求，避免伪造通知消耗平台额度。
- 定期分页补查，保留重叠窗口且去重，不只查首页或依赖通知永不丢失。启动后能恢复未处理任务；不保存不必要的完整通知及地址字段。
- 验证 OAuth 身份与订单身份的匹配方式；不能用昵称匹配。已登录且曾付款的用户可以直接管理资料，无需再次付款。
- 对昵称作长度验证和纯文本输出；对头像验证实际文件内容、限制解码资源、重新编码并移除元数据。不接受 SVG 或任意远程 URL 抓取。避免孤立上传文件长期堆积。
- 发布条件检查、订单入库与资料关联必须可重试；公开名单版本随发布结果更新。退款状态若平台能力不足，明确记录限制，提供所有者手动纠正入口。
- 管理员首版可通过受保护的本机管理命令操作，避免为少量运营工作建设完整管理平台；不得暴露无鉴权管理接口。
- 数据库和头像必须在部署目录外持久化；备份采用一致性方式，验证恢复。部署前确认现有服务、端口与反向代理，不覆盖未知配置。
- 日志脱敏，密钥仅部署环境可读；准备健康检查、同步错误记录及故障定位步骤。退款、关闭公开与历史导入操作保留必要审计记录。
- 交付部署/恢复说明、环境变量名称清单（无值）、契约夹具、能力验证结果及正式入口。

## 8. Dela AI 实施清单

先重新读取 AGENTS.md、技术规划和相关技能，检查当前工作区，保留他人改动。重点位置：

- `src/renderer/features/settings/sections/AboutSection.tsx`：在线名单和赞赏入口。
- `src/renderer/features/settings/credits.ts`：保留作者配置，线上迁移完成后移除不再使用的 Sponsors 硬编码；不要提前删除现有展示。
- main/preload/shared：按现有目录和接口惯例增加最少的名单获取与打开页面能力，禁止 renderer 导入 main。

具体要求：

- main 请求固定 origin 的公开 API并验证响应；preload 暴露有限操作，不提供任意 URL 抓取或打开接口。缓存沿用现有合适机制，不新增数据库层级或云账号。
- renderer 只取得公开数据及本地加载状态；图片仅解析为批准 origin 下的头像路径。核实 Electron/CSP 允许范围，拒绝路径逃逸及不受控跨域重定向。
- 进入关于页、关于页可见时窗口重新获得焦点、用户手动刷新时请求；合并并发刷新并适当退避，不在后台长期轮询。
- 有缓存先展示缓存，再后台刷新；刷新失败不闪成空白。首次无数据失败显示重试入口，合法空列表展示空态；头像失败用默认头像。
- 缓存记录本地成功检查时间，与服务端 updatedAt 区分。最大保留期按冻结契约执行；离线缓存可能暂时保留已撤回资料，页面与隐私说明不能承诺所有离线副本即时删除。
- 返回浏览器后不显示“你已付款”，因为客户端没有可靠个人身份；仅刷新公开名单。
- 使用现有 UI 组件与设计 token，不引入新的动画依赖。动画效果由用户审阅，不使用 Playwright 或多帧探针验收动画。
- 首版不增加公共人物链接字段、实时推送、赞助等级或金额展示。
- 更新相关接口文档、技术规划、devlog；实际面向用户上线时再更新 README 与隐私说明，不提前宣传未验证能力。

## 9. 两个 AI 的同步协议

### 单一事实来源

本文件保存在 Dela 仓库，作为产品边界与跨端契约的主文档。ECS 仓库保存收到的副本，并注明来源 Git commit 和计划版本；不能形成两份独立演进的契约。服务器内部细节由 ECS 仓库文档维护。

双方通过所有者转交交接包，或在所有者明确授权的协作渠道沟通；不能假设两边共享文件系统、能看到对方聊天或自动收到文档更新。不在聊天传密钥和真实订单。

### 变更规则

1. 提议方提交“变更原因、旧/新示例、兼容影响、受影响任务”，不先偷偷改接口。
2. Dela AI 将双方已评审结果合入本文件并递增计划/契约修订号；ECS AI 更新副本引用。
3. 双方分别确认已接收相同修订号及提交，随后实施。只确认自己一侧不能视为完成同步。
4. v1 增加可选字段可以保持兼容；删除字段、更改类型、语义或必要行为必须使用新 API 版本，保留旧版本供已发布客户端使用。
5. 未达成一致的部分标记阻塞；可以继续不依赖该部分的工作。用户最新明确决定优先，随后同步文档。

| M3 真实闭环 | 配合所有者完成一笔授权的小额真实赞助并核实订单 | 验证返回应用刷新与资料变化 | 同一真实赞助者完成首次发布、修改、撤回，名单结果一致 |
| M4 上线 | 备份恢复验证、正式配置、回滚说明 | 正式地址、发布检查、用户文档 | 所有者确认上线；双方交接记录完整 |

M0 验证外部权限期间，Dela 可以做不依赖权限的代码调查；契约冻结后两端可同时开发 M1。OAuth 阻塞不要求停止公开名单的独立开发，但完整自助功能不得宣称完成。

## 11. 联调验收与发布顺序

集中在功能基本完成后执行相关检查，不为文档变化运行打包。每端依据实际改动选择针对性测试；涉及 Dela 构建或原生依赖时按项目约束执行 build、smoke 和打包后启动。

最低验收矩阵：

| 场景 | 预期 |
| --- | --- |
| 未付款或伪造通知 | 不取得展示资格；伪造资料归属失败 |
| 相同订单多次通知、同人再次付款 | 订单不重复、公开人物不重复 |
| 通知漏发、服务重启 | 补查和恢复任务最终处理成功 |
| OAuth 标识匹配、另一用户尝试修改 | 本人可编辑，他人被拒绝 |
| 用户未选择公开 | 查单成功也不出现在公开响应中 |
| 资料修改、取消公开、管理员隐藏 | revision 与 ETag 更新；客户端刷新一致；隐藏不会自动解除 |
| 200 空名单、304、429、503、超时、坏响应 | 分别按契约处理，不错误清空缓存或密集重试 |
| 非法头像、损坏图片、特殊字符昵称 | 上传被拒或安全显示，无脚本执行、跨域抓取或页面破坏 |
| 旧客户端读取新版服务 | v1 保持兼容，无私人字段泄露 |
| 备份恢复、发布回滚 | 订单、资料及头像一致；不丢已核实记录 |

先部署保持 v1 兼容的 ECS，再发布 Dela。联调数据不得出现在正式名单。真实付款只能由所有者操作或明确授权执行，不把支付交易当作普通自动化测试。

后端回滚不删除持久化数据；若涉及数据库迁移，先准备可恢复备份与兼容策略。客户端请求失败仍可按缓存规则工作；紧急撤下公开列表用合法空名单和新版本，不用 503 代替撤回，因为 503 会保留旧缓存。断网设备只能在重新联网或缓存到期后移除旧展示。

## 12. 可直接交给两个开发 AI 的任务说明

### 给 ECS AI

阅读本计划及 ECS 仓库自身约束。先报告当前仓库/部署环境、爱发电 API 和 OAuth 的验证方式及缺失输入，完成 M0 所属事项。只开发 ECS 后端与赞助网页；与 Dela AI 按第 6、9 节冻结接口、交换同版夹具和交接记录。不能假定 OAuth 已开通，不凭用户提交的订单号认领，不把 Webhook 原文当作到账事实。保护已有 ECS 服务，密钥留在部署环境。按里程碑交付，明确真实验证与待验证部分；阻塞外部能力时继续独立工作并报告依赖。

### 给 Dela AI

先读 AGENTS.md、docs/technical-plan.md 和本计划，检查工作区已有改动。只承担第 8 节桌面端任务，不实现支付与网页身份系统。在 M0 评审并确认接口版本，M1 消费同版夹具，在 M2 切换实际服务联调。main/preload 提供有限公开名单能力，保留 renderer 隔离与单 package 边界。不要因 ECS 未就绪而伪造完成状态；按第 9 节交接结果并更新项目文档，按实际改动执行相关检查。正式名单接管前保留已有赞助者展示，迁移名单必须与 ECS AI 核对。

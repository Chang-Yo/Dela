# 0001. 按功能组织的模块化单体，Core 是唯一的硬边界

- 状态：已接受
- 日期：2026-11-09

## 背景

v2 的目录按进程划分（main、preload、shared、renderer）。2026 年的 202 个 `feat` 提交中，53% 改动了 4 个及以上区域：一个功能被拆成四份，开发者很难判断该改哪里。Dela 的变化来自功能，而不是来自技术层。

Dela 是单用户桌面应用，响应延迟主要取决于 LLM。可伸缩性、弹性和极致性能都不是优化目标。

## 决定

保持单一部署单元，内部按功能划分为五个顶层目录：

| 目录      | 内容                                       |
| --------- | ------------------------------------------ |
| `core`    | Agent 内核与 Agent 协议，只依赖 Node 和 Pi |
| `ui`      | Design System，零业务依赖                  |
| `modules` | 通用功能：没有交大也成立                   |
| `sjtu`    | 交大功能：离开交大就没有意义               |
| `app`     | Electron 入口、工作台外壳、模块清单        |

每个模块的结构统一为 `index.ts`（唯一出口）、`contract.ts`、`main/`、`view/`、`data/`。

Core 采用微内核结构：工具、Skills、MCP、dela 命令域和资源解析都通过注册表接入，Core 不认识任何具体业务。所有模块在 `app/modules.ts` 中显式列出，不做自动扫描。

依赖规则由 CI 检查：

1. `core` 只依赖 Pi 和 Node；`core/protocol` 只依赖 zod。
2. `ui` 只依赖 react、radix、cva、lucide。
3. 模块之间只通过对方的 `index.ts` 引用；`view/` 只能引用 `core/protocol`，不能引用 `main/`。
4. `core`、`modules`、`app` 不能引用 `sjtu`，`app/modules.ts` 除外（见 0005）。
5. 模块只能引用 `app/module.ts`，不能引用 app 的其他部分。

## 后果

- 一个功能对应一个目录，改动范围可以从目录结构预测，PR 标签也能按目录自动生成。
- Core 可以单独通过类型检查，也可以单独开源。
- 构建需要从每个模块的 `main/` 和 `view/` 收集入口，初次搭建比按进程划分复杂。
- 注册表让“某个命令在哪里注册”不再一眼可见；显式的模块清单是对这一点的补偿。
- 不拆分进程，也不引入微服务。

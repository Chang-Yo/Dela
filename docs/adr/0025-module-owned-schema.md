# 0025. 模块自带表结构与迁移，宿主统一执行

- 状态：已接受
- 日期：2026-11-21

## 背景

Dela 打算把去掉 `sjtu/` 后的完整产品开源，供其他人 fork 后加入自己的模块，`sjtu/` 就是这种定制的示范。但现在所有表的结构都写在 `app/main/database.ts`，迁移按 `user_version` 排成 v6→v17 一条编号链。这带来几个问题：

- 加一个带表的模块，就得改 app；去掉 `sjtu/` 后，app 仍会建出交大的表。
- fork 的人自己加了“第 18 步”迁移，上游也加一个“第 18 步”，编号就撞了，已经升到 18 的用户会跳过上游这一步。
- 模块直接用 SQL 读写别的模块的表，lint 管不到，所以每张表的结构实际上都是公共接口。
- `notifications.source` 用 CHECK 限定了四个来源，新模块一写入就会失败。

Rails、Django 和 Discourse 插件的做法是：迁移按名字登记，库里记一张“已执行清单”，各个插件或应用的迁移放在自己的目录里。Flyway 的 baseline 与 Django 的 squash 用来让新库从当前结构起步，不重放历史。

## 决定

- **仍然只有一个 `dela.db`**，由宿主打开、执行迁移和备份。
- **谁的表谁声明**：core 与各模块在自己的 `data/` 里放当前的建表语句和迁移，经模块定义交给宿主。宿主不写任何业务表。
- **只有表的主人写自己表的 SQL**。别的模块通过对方 `index.ts` 导出的函数读写，由检查脚本把关。迁移不受此限，但只能改自己的表和别的表里属于自己的数据（例如自己的 id）。
- **迁移按名字登记**：文件名用 `YYYYMMDD-简述`，记录在 `schema_migrations(module, name)` 中。启动时按日期（同日按模块 id）执行清单里还没有的迁移，全部成功才提交，任何一步失败都整体还原。
- **新表直接按当前结构建**：模块第一次出现时（清单里没有它），先建表，再把它已有的迁移全部记为已执行。
- **跨模块外键只能顺着代码的依赖方向**，不能指向 `sjtu`。`sessions.project_id → workspace_entries` 是 core 指向模块，方向反了，要去掉。删除项目时，workspace 本来就先删会话。
- **`workspace_settings` 归宿主**，作为共享的键值存储。新的键以模块 id 开头，现有的键不改名。
- **旧的 v6→v17 链改为一次性的“旧版过渡”**：只给 Dela 老用户用，执行完后把 v17 记为所有模块的起点（baseline）。开源版没有历史数据，所以不带这段代码。何时删除由维护者另定。

## 后果

- 加模块只需新建目录、在清单里加一行。去掉 `sjtu/` 后，交大的表和迁移随之消失。
- fork 的人合并上游时，迁移不会撞号。代价是迁移之间没有显式依赖，只按日期排序；需要先后关系的迁移由作者按日期安排。
- 去掉 CHECK 和外键都要重建表。这两次改动作为新机制下的第一批迁移。
- 迁移 README 中“迁移代码一直保留，不删除”一条，改为“过了支持期可以合并为新的起点”。
- 本记录部分取代 [0016](0016-core-host-boundary.md)：表结构与迁移不再归宿主，“等出现第二个宿主再说”的前提也不再成立。

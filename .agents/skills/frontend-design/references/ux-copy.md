# UX 与文案

**从用户角度出发：理解用户为什么打开这个页面、为什么点这个按钮。**
**文案永远把读者放在第一位，学习 Apple 的文案风格。**

## 文案

1. 简洁、直白、无歧义。能用一个词说清楚的，不用一句话。
2. 标题与描述成对出现时，标题要能统领描述，或代表描述的本质。读者只看标题，也应该知道这一块讲什么。
3. 不把开发者的意图写进界面。屏幕上不出现「本模块用于……」「为了方便你……」「此处展示……」这类说明设计目标的句子。
4. 按钮本身已能表达动作时，删掉旁边的功能描述。「保存」旁边不需要再写「点击保存你的修改」。
5. 默认用户对软件和 Web 界面有基础认知，只在必要时才给提示文本。
6. 同一个概念在全站只用一个词，不要「删除 / 移除 / 清除」混用。

示例（仅示意风格）：

| 不好                                   | 好                   |
| -------------------------------------- | -------------------- |
| 点击下方按钮即可开始创建你的第一个项目 | 创建项目             |
| 此区域用于展示你最近的活动记录         | 最近活动             |
| 操作失败，错误码 500                   | 保存失败，请稍后重试 |

## ICON 与文字标签

取舍顺序：

1. 语义明显的纯 ICON（关闭、搜索、设置、返回）
2. ICON + 悬浮提示（tooltip）
3. ICON + 文字标签

界面里 ICON 太多、含义不够直观时，用悬浮提示或「ICON + 短标签」来解决，不要堆长句。

## 状态与错误

- 异步操作必须有反馈：加载中、成功、失败，三种状态都要有。
- 错误信息用人话，不出现错误码。写清楚哪里出了问题，并给出下一步怎么做。
- 空状态说明接下来可以做什么，不只是写「暂无数据」。

## 危险操作的二次确认

按严重程度分两档，不要混用。

**常规敏感型**（如归档久远的聊天记录、清空已读通知）

- 特点：可以恢复或影响较小，用户会高频使用
- 做法：在原按钮的位置直接切换为确认步骤（例如按钮变成「确认归档」，几秒后自动恢复），不打断当前流程

**不可恢复型**（如彻底删除用户数据、重置所有设置）

- 特点：做了就回不去
- 做法：弹出专门的确认框，让用户聚焦于这个动作本身
- 确认框里写清楚后果，按钮文字用具体动作（「删除账号」），不用笼统的「确定」
- 危险按钮与取消按钮在视觉上要明显区分，默认焦点放在取消上

## 用户控制

- 能撤销的操作优先提供撤销，比确认框更轻。
- 任何弹层、流程都要有清晰的退出路径。
